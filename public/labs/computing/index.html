An introduction to computing and software

Examine how a precisely stated problem becomes a system whose behaviour can be tested.

What does computing study?

Computing investigates how information can be represented and processed, which problems can be solved by algorithms, and what resources a solution requires. It includes programming, but also mathematical reasoning, data structures, computer systems, networks, security and the interaction between people and technology.

Computer science

You investigate methods and their properties. Can a procedure solve the problem? Does it terminate? How does its cost change as the input grows? What can its results establish?

Software engineering

You turn requirements into dependable software. The work includes clarifying a brief, implementing and reviewing code, testing unusual cases, documenting decisions and maintaining a system as needs change.

How the subject is studied

Expect to move between explanation and construction: read a specification, reason through an algorithm, write a programme, observe a failure and revise your understanding. A programme that runs can still produce the wrong result. Testing requires a reasoned account of what should happen before you inspect what actually happens.

Harvard’s CS50 course outline illustrates the breadth of introductory study, including algorithms, data structures, memory, databases and web programming. This Lab samples a narrower task: investigating and repairing business logic.

Your investigation

A fictional community centre uses a small programme to reserve workshop seats. Its prototype violates the booking rules. You will define expected behaviour, diagnose three logic defects, locate and repair the faulty logic, build tests, then adapt the system to cancellations before writing a handover note.

Your output: a student-designed test pack, three evidence-backed diagnoses, a tested repair, a cancellation extension and an engineering handover. No installation or prior coding experience is required. The workbook teaches the notation and includes a bounded test runner. Allow approximately 3–5 hours; this is an unvalidated planning estimate.

The fixed questions and test outcomes have definite answers. Your written explanations can use different wording if they accurately connect a rule, the faulty behaviour and the correction. This is not a timed coding contest or a career-fit assessment.

Understand the system before changing it

The specification determines correct behaviour. The prototype may disagree.

Workshop Desk: the booking rules

  1. Start each scenario with its stated remaining capacity and no accepted IDs. Process requests in order. State persists within the scenario; start fresh for the next scenario.
  2. IDs are case-sensitive. Supplied IDs are valid. Counts are whole numbers. Decimal counts, missing IDs, networks and simultaneous requests are outside this exercise.
  3. First, counts below 1 or above 3 return INVALID.
  4. Otherwise, an already accepted ID returns DUPLICATE.
  5. Otherwise, a request exceeding remaining capacity returns FULL. Exact fits must be accepted.
  6. Otherwise, deduct the requested seat count, record the ID and return ACCEPTED.
  7. Rejection changes neither capacity nor recorded IDs. An ID used only in a rejected request can be tried again.

Read the notation

A variable holds a value; remaining = remaining - seats subtracts the requested count. IF tests a condition. RETURN ends the current request immediately. Indented returns occur only when their IF condition is true.

AND requires both statements to be true; OR requires at least one. > excludes equality; >= includes it. IN checks membership of a set; ADD records an ID. A set remembers membership, not a quantity attached to each ID.

Different worked example: a shop has 7 notebooks. A valid purchase of 2 leaves 5. A later request for 6 is rejected and leaves 5. A trace records input, result and retained state after every request, including rejections.

The prototype

01  FUNCTION reserve(id, seats)
02      IF seats < 1 AND seats > 3
03          RETURN INVALID
04      IF id IN accepted_ids
05          RETURN DUPLICATE
06      IF seats >= remaining
07          RETURN FULL
08      remaining = remaining - 1
09      ADD id TO accepted_ids
10      RETURN ACCEPTED

There are three deliberate logic defects. Line numbers are references, not hints about which lines are wrong. Your repair must retain all other required behaviour.

Construct four small test scenarios

Between your four tests, expose all three defects and include at least one scenario that the original prototype already handles correctly. This last test checks for regression: a repair must preserve correct behaviour. You may use different inputs from another student.

For each test, enter starting capacity and 1–4 requests. One request per line, written ID, seats. Use an uppercase ID of 1–8 letters/digits beginning with a letter. The requirements change: support cancellations

Reconsider the information the programme stores, not just the expressions it evaluates.

The new brief

Keep all booking rules. Now allow CANCEL id. If the ID has no active booking, return NOT_FOUND and change nothing. Otherwise restore exactly the seats in that booking, remove the active booking and return CANCELLED. Cancelling the same booking twice must not restore seats twice. Once cancelled, the ID may be booked again. There are no payments or refunds in this case.

Starting scenario: 8 seats. Process BOOK A for 2, BOOK B for 3, CANCEL A, CANCEL A. Predict what happens before running the extension.

Learning note: store a value with each ID

A set can tell you that an ID exists. A mapping stores a value alongside it. In an unrelated stationery example, orders["Z"] = 4 records four notebooks for order Z; reading orders["Z"] retrieves 4. Removing the record means it is no longer an active order.

The cancellation skeleton first checks for an active record. If none exists, it returns NOT_FOUND immediately. Otherwise it reads the saved value, restores a quantity, optionally removes the record and returns CANCELLED. Reading happens before removal. You choose what the booking record holds, what to restore and whether to remove it. BOOK uses your verified repair.

Explain what the original set can and cannot tell you, what the new record must retain, and why the order of lookup, restoration and removal matters.
